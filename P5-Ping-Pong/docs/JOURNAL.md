# Journal

One line per surprise, failure or fix. This is the raw material for the Notion
reflection bullets (What we learned / most proud of / What took a while / Most
spectacular failure), so write it down when it happens, in your own words.

- 2026-10-06 — The plan went through two adversarial reviews. The schedule reviewer said my first compressed plan was "not realistic as written" (G0 by Thursday only ~35–45% likely); the plan was rebuilt around 4.5 h/days, Claude night shifts and a clock ladder.
- 2026-10-06 — Found a `P4-Door-To-Door-Service` folder committed at 19:56 by another session, so this project is **P5**, and P4 may compete for the same hours.
- 2026-10-06 — A magnitude-only swing detector fires on the *backswing* 100% of the time in a reviewer's simulation; the detector projects onto a learned signed forward axis instead.
- 2026-10-06 — Bluetooth cannot be used from the Claude desktop app's shell (macOS aborts the process, TCC); all BLE/camera runs happen in Terminal.app, and the tools now say so instead of crashing.
- 2026-10-06 — My own `FakeEnv` quantised the hub rate (66 Hz measured as 60, 33 Hz as 20) because it dropped fractional time between sleeps; the env_check tests caught it before any hardware did.
- 2026-10-06 — The first whole-pipeline run on fake hardware passed 14 of 14 tests at once, which I did not trust. Mutating the wiring (no haptic blank windows, no poses fed to the judge) made exactly the right tests fail, so they were measuring something.
- 2026-10-06 — The fake rally showed that in a first rally every hit is technically a "new record", so the 5-pulse record buzz replaced the hit-quality cue on every single hit. The record cue now fires once per rally, only when a previous best is passed.
- 2026-10-06 — A hub that went quiet for the stale limit (300 ms) was scored as a *miss*: the miss deadline passed on the wall clock before the pause started. Two fixes: a miss now waits until the IMU data has reached its deadline, and a pause is back-dated to the last sample, so the ball resumes where the player last saw it.
- 2026-10-06 — The haptics actuator held its lock during BLE writes, so the 60 Hz game loop could stall behind a buzz. Split into a schedule lock and a device lock; a test with a deliberately slow device pins it.
- 2026-10-06 — A swing plus its backswing looks periodic, so a bare FFT "shake" check would lock the paddle after normal swings. The shake rule needs a dominant 3-8 Hz bin, a narrow peak, enough amplitude and at least four sign reversals; white noise lands its loudest bin in the band about one time in five, and only the narrow-peak test stops it (checked by mutation: 92 false locks without it).
- 2026-10-06 — Wiring the recorder in, the swing event's own `kind` field collided with my helper's `kind` argument (a TypeError that the end-to-end tests caught within a second); and the test file that covered the rig crossed the 500-line rule, so the builder tests moved to their own file.
- 2026-10-06 — The calibration tool recovers a hub mounted at an arbitrary angle (axis error 0.16 degrees on the scripted person) and the detector then recognises 10 of 10 of the calibration swings; with the unit guess wrong by 4x it stays self-consistent. The first version drew a 720p frame on every 10 ms step and made one test take 28 s, until rendering was throttled to the camera's 30 fps.
- 2026-10-06 — Replaying a recording reproduces every decision of the live session at the same instants (serves, hits, misses, verdicts, pauses), and the same recorded sensor data can be re-judged with other settings: a swing 252 ms late that J1 rejected becomes a hit with a 0.4 s window. My first replay "paused" at the end because I let it run 1.5 s past the data, so the hub looked silent again.
- 2026-10-06 — Load rehearsal with the real MediaPipe model: inference is ~10 ms a frame, the camera thread holds 30 fps, and the game loop (60 Hz, 720p HUD) stays at 6.7 ms p95 with it running, so one Python process is enough. The rehearsal also exposed that MediaPipe rejects any timestamp at or below the last one *its landmarker* saw, so a second worker got a flood of errors; the worker now uses the clock's absolute milliseconds and reports a repeating error once, not 30 times a second.
- 2026-10-06 — The first render of the end-of-game leaderboard put the rows on the net line and collided with "SPACE to play again": I only saw it by rendering the screen and looking at it, not from any test. It is now a panel at the left with the player's own row in green, and a test checks that nothing else on the screen moves.
- 2026-10-06 — The spin classifier scores 100% cross-validated on swings simulated through the real detector, but my first toy test (one useful feature among twelve, with "flat" in the middle) only reached 67% for any regularisation strength: a classifier cannot make up for a badly built problem, so the test data was fixed, not the model. With real swings the honest number is whatever `./pp train_spin` reports, and below 75% the game stays flat.
- 2026-10-06 — A replay with spin would not have reproduced the session (spin changes the ball's flight time, so every later serve moves): the rig now records the probabilities it used for each swing and the replay reuses them, which is the same trick as recording the start time.
- 2026-10-06 — Wiring the Q-learning opponent, my first policy test failed because the learner's state includes the column of the last zone it served: after the first serve to the right-hand column the state changed and a bonus I had set for one state no longer applied. The opponent was right and the test was wrong; the bonus belongs on every state.
- 2026-10-06 — A learning opponent cannot be replayed exactly (its serves depend on a table the recording does not contain), so recordings carry a `learn` flag and `./pp replay` warns instead of pretending.
- 2026-10-06 — My fake hub accepted any keyword arguments, so a misnamed BLE argument (`color=` for `card_color=`) would have passed every test and failed on the hardware. The fakes now bind every call to the real library's signature; it found nothing wrong in the code, but a typo can no longer hide. Also learned that the library starts the hub's battery level at 0 until the first report, so "battery 0%" is now shown as unknown.
- 2026-10-06 — Re-reading the README against the code I found that judge gate J4 ("camera and IMU agree on the moment") was only a label that always said "logged-only": it measured nothing. It now measures how far the camera's hand-speed peak is from the IMU's swing peak, never blocks a hit, and `./pp report` turns the median into a suggested CAMERA_LAG_S, a second measurement of the camera lag taken from real play.
- 2026-10-06 — The README claimed a PD controller for the computer's paddle, but the code only had a closed-form "reach" formula: I wrote the claim from the plan, not from the code. Instead of deleting the claim I built the controller (reaction delay, then a saturated PD velocity command; the screen now draws the computer's paddle chasing, or missing, your shot) and added a test that every algorithm named in the README's (c) table exists in the module it points at. The simulator shows the effect: Pro now misses 11% of medium swings instead of 4%, because the controller needs time to settle near the edge of its reach.
- 2026-10-06 — A fuzz of the swing detector with 240,000 random, spiky, clipped samples at uneven spacing found that an IMPACT could be dated after the sample that produced it: the parabola through the peak lands outside its neighbours when a Bluetooth gap sits right before the peak. The peak time is now clamped between its neighbouring samples, and a compact version of the fuzz stays in the tests.
- 2026-10-06 — A chaos test runs the whole pipeline on fake hardware with random hub and camera blackouts, shaking, weak or late swings, motor vibration and restarts, then checks the invariants: the published score only rises and never exceeds the record, no game event happens during a pause, balls are numbered in order, the record never falls. 200 longer sessions found no violation, and a mutation that makes the game ignore pauses is caught in 7 of 10 sessions, so the test is not vacuous.
- 2026-10-07 — `env_check` told me that below 25 Hz "the swing source switches to the pose wrist-speed detector", and there was no such detector: the plan's fallback had never been built, only promised in a message. I built it as a *virtual gyro*: each accepted pose becomes one pseudo-IMU sample whose gyro vector is the hand's velocity, so the same signed-axis detector, shake lock, judge, recorder and replay run on it unchanged (`pingpong/posegyro.py`).
- 2026-10-07 — The first try on hand velocity found nothing: at 30 fps a fast swing rises from rest to its peak in one frame, and the hub's one-sample "spike" gate threw every real swing away. The camera's detector settings now turn that gate off and ask for a 100 ms minimum instead (a one-frame landmark jump rises in a single sample, a real swing needs two); a mutation of each setting is caught by a test.
- 2026-10-07 — Playing the fallback on the scripted player exposed two defects that are just as true for the hub: a swing that armed the very sample the cool-down ended was measured from a stale onset (the last idle moment before the *previous* swing) and rejected as a second long, and a stroke that began one sample before the cool-down ended was swallowed by it. A quick sideways move of the hand to the ball looks like a swing to a camera, fires early (the judge ignores it) and its cool-down then ate the real stroke; the camera's cool-down is 0.15 s instead of 0.3 s, and the detector now leaves the cool-down once its time is up and the forward rate has dropped since the impact.
- 2026-10-07 — First contact with the real public broker (on scratch topics outside `ME193/`): TCP connects instantly, but the broker closed three of the first four MQTT connection attempts without an answer and accepted the fourth after 8 s; once connected, the score published QoS 1 retained, a late joiner read the retained `3.0` and the "online" status, and I cleared both topics afterwards. The reconnect back-off was 1-30 s, which would have left the score offline for half a minute after a bad stretch; it is now 1-5 s.
- 2026-10-07 — Rendering the lobby with the long "UNCALIBRATED: run ./pp calibrate_swing ..." hint showed it running off both edges of the screen and across the score: no test could have said so, only looking at the image. Messages now shrink to fit (and wrap or cut with "..." as a last resort), standing lobby notices sit below the start prompt, and a test checks nothing is drawn within 20 px of an edge.
- 2026-10-07 — The plan said a restart must not wipe the score, but a plain run starts from zero by design ("best streak this run"), so *any* later session, a rehearsal after the graded take, would publish 1.0 over a retained 18.0. The game now subscribes to its own topic (read-only), says what the broker holds in the lobby and the console, and `--resume` keeps that value as the best to beat.
- 2026-10-07 — Making the camera the swing sensor meant the scripted hand finally moved *during* the swing, and the judge's pose gate (J2) started failing hard swings at Club and Pro: the gate looks at the hand over the 300 ms before the peak, and a swinging hand covers a shoulder width or more in that time. The fakes had always held the hand perfectly still while the gyro swung, so this had never shown up. I did not change the radii on a hunch (real data will say), but added `--set level.radius_sw=0.8` to `./pp play`, recorded with the session and honoured by `./pp replay`, so the first real recording can be re-judged with other radii in one command.
- 2026-10-07 — Every test so far ran on one thread and a simulated clock, but `./pp play` is five threads in real time, and the first real-hardware run is the worst place to learn about a deadlock. A rig with a "BLE" thread at 66 Hz, a camera thread blocking at 30 fps and the real IMU/actuator/vision workers found nothing wrong (it needed a lock in my own scripted player, three threads read it), and a 3-minute run with the 720p HUD drawn every frame played 221 hits in a row: loop 7 ms median, 11 ms p95, memory flat at ~154 MB, no thread errors, nothing swallowed by a worker, clean shutdown under 3 s. The same two tests pass five times in a row and with all 8 cores busy.
- 2026-10-07 — `env_check`'s MQTT check failed one time in four against the real broker: it connected once and gave up, and the public broker closes a connection attempt without an answer often enough that two or three drops in a row are normal ("no echo within 5 s (outbound 1883 blocked?)" would have sent me off blaming the firewall). The fix is to connect in the background and keep retrying (0.5-2 s) inside a 10 s window; 8 of 8 round trips now succeed, a few of them after dropped attempts. To pin it without the internet I wrote a 130-line MQTT broker for the tests (CONNECT with a will, QoS 0/1 PUBLISH, retained messages, wildcards, and a switch that closes the first N connections); the real paho client now also runs against it for the score path: late joiner, last will on a dead connection, a score published while the broker is unreachable, `--resume`.
- 2026-10-07 — Reading the code for what would hurt most on the first real run: an exception in one frame of the main loop (a bug only the real sensors trigger) would have ended the whole session, and an unreadable Bluetooth packet would have aborted the notification callback. Both are now survivable: a frame that raises is reported once per source line and skipped (30 in a row end the session with the error, Control-C is never swallowed), and a packet the parser cannot read is counted and the stream goes on.
- 2026-10-07 — First real bench (hub at 63.9 Hz, worst gap 93 ms) and two of my unit guesses were wrong: the gyro is 0.99 counts per deg/s, not 10 (every dps threshold had been 10x off), and the accelerometer, about 1017 counts per g, saturates at 8011 (~8 g) in a hard swing while the gyro never clips. `bench_hub` mixed the two channels and wrote the accelerometer's 8011 into my config as the *gyro's* full scale; its clip analysis is per channel now and I removed the bad key from `config_local.json`.
- 2026-10-07 — The swing detector, built and tuned on scripted 150 ms pulses, found 1 of my 20 real soft swings and 3 of 20 hard ones: a real stroke builds up for ~0.5 s with shoulders and hesitations, ends in a long tail, and the backswing is as big as the stroke. It now tracks the peak on the forward rate, fires when that falls to 65% of its peak (or the peak is 0.12 s old and the rate is below it), allows 1.2 s from arming and 2 s durations, and its threshold is 0.7 x the soft-swing strength (my weakest deliberate soft swing was 0.81 x the median one, a stroke's own recovery lobe up to 0.65 x). On the recorded forward swings it gives exactly one impact each, at the true forward peak (+-12 ms, peak within 1.7%), 33-148 ms after it, and none on the backswing-only takes.
- 2026-10-07 — My first regression test of that retune passed 52 of 53 cases for the wrong reason: most real takes start mid-backswing (I am already moving at the GO beep), and I used the take's first samples as the "rest" offset, both for the quiet lead-in fed to the detector and for the true peak, so a soft swing read 657 dps when its forward peak is 421. The two errors cancelled until one max-effort take (771 against 1181) did not. The offset is now the hub's measured rest offset, `forward_peaks` requires it instead of guessing, and the tolerance went from 12% to 5%: the detector's peak matched within 1.7% all along.
- 2026-10-07 — Real shakes and waves are ~2 Hz (1.6-2.4), not 3-8 Hz, so the shake lock now takes 1.2-8 Hz over 1.5 s. The full gate then caught that camera-only mode, whose scripted reposition-then-swing rhythm sits near 2 Hz, got its paddle locked for good (10 tests failed, 0 hits in 120 s): the camera keeps its original 3-8 Hz / 1 s band, since it has never seen a real camera recording.
